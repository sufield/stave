# Prowler S3 Coverage

Cross-reference of Prowler's 21 AWS S3 checks against Stave's S3 control catalog,
generated by inspecting `prowler-cloud/prowler/prowler/providers/aws/services/s3/`
on the upstream master branch. The PARTIAL and NOT COVERED rows are the
candidate backlog for future S3-scope iterations.

This is the first slice of a broader methodology-coverage effort. IAM, EC2,
and other services, plus ScoutSuite's S3 checks, are separate follow-up scans.

## Summary

- **Prowler S3 checks surveyed:** 21
- **COVERED:** 17
- **PARTIAL:** 3
- **NOT COVERED:** 1
- **OUT OF SCOPE:** 0

### Candidate backlog (high-signal gaps, ordered by Prowler severity)

1. **`s3_bucket_shadow_resource_vulnerability`** (high) — PARTIAL. Stave's
   `CTL.S3.BUCKET.TAKEOVER.001` catches dangling / wrong-owner references, but
   does not enumerate Prowler's predictable service-name patterns
   (`aws-glue-assets-<account>-<region>`, `sagemaker-<region>-<account>`, etc.)
   and flag buckets that *should* exist under those names but are owned
   elsewhere. Needs a contract extension (e.g.
   `storage.shadow_resource.name_pattern_matches`) plus a new control.
2. **`s3_bucket_kms_encryption`** (medium) — PARTIAL. Stave requires KMS only
   for PHI/sensitive-tagged buckets (`CTL.S3.ENCRYPT.003`,
   `CTL.S3.ENCRYPT.004`). Prowler's check expects every bucket to use SSE-KMS.
   This is a posture-policy difference, not a technical gap — a future
   iteration could add a generic "KMS required account-wide" control behind
   a tag or profile flag, leaving the tagged-only controls in place.
3. **`s3_bucket_event_notifications_enabled`** (low) — NOT COVERED. Stave has
   no generic S3 event-notifications control; `CTL.S3.BREACH.DETECT.001` uses
   event-notifications only as one signal inside a PHI-specific composite.
   Low Prowler severity so low-priority backlog.
4. **`s3_bucket_cross_region_replication`** (low) — PARTIAL. Covered only for
   PHI-tagged buckets (`CTL.S3.REPLICATION.002`). The tag-gated scope is
   arguably correct posture policy; document the choice rather than lift.

## Notes on structural differences between Prowler and Stave

Prowler typically has **one check per configuration signal**, which produces
narrow checks that map one-to-one to AWS API fields. Stave often **splits a
Prowler check across two or more controls** when the underlying configuration
has multiple remediation paths: `s3_bucket_public_write_acl` covers
`WRITE` + `WRITE_ACP` + `FULL_CONTROL` in one check, whereas Stave separates
`FULL_CONTROL` (`ACL.FULLCONTROL.001`, critical) from `WRITE_ACP`
(`ACL.ESCALATION.001`, high) from plain `WRITE` (`PUBLIC.003`, critical via
the composite) because the remediations and severities differ. The union
of Stave's controls catches what Prowler's single check catches; the
split gives operators specific remediation guidance.

Similarly, Stave's per-PAB-sub-flag controls (items 2 and 9) give the operator
a one-command fix per flag, which Prowler's single umbrella-style check does
not. The additional granularity is not visible in the COVERED status but is
meaningful for remediation cost.

## Out of scope for this slice

- **Prowler checks outside the S3 service.** IAM, EC2, RDS, and other services
  need their own coverage scans. This document tracks S3 only.
- **ScoutSuite's S3 rules.** ScoutSuite may cover S3 configurations Prowler
  does not; a follow-up scan will diff ScoutSuite against both Prowler and
  Stave to surface ScoutSuite-unique checks.
- **CIS Benchmarks and other external frameworks.** Those are a separate
  corpus with their own coverage-tracking story.
