# Debugging Reference — The Debugging Book (Andreas Zeller)

Techniques mapped to Stave development. Source: [debuggingbook.org](https://www.debuggingbook.org)

| Technique | Core idea | Stave application | When to reach for it |
|-----------|-----------|-------------------|----------------------|
| [Tracing](https://www.debuggingbook.org/html/Tracer.html) | Instrument execution to record what happened — variable states, function calls, branches taken. | Add structured trace output to invariant evaluation: which fields were read, which predicates were evaluated, what values triggered the rule. Use `--trace` flag in dev mode. | Invariant fires on a config you didn't expect, or silently doesn't fire when it should. Need to see the evaluation path. |
| [Assertions](https://www.debuggingbook.org/html/Assertions.html) | Encode assumptions as executable checks that halt on violation, turning silent corruption into loud failures. | Assert structural invariants at Composition Root boundaries — e.g. the config snapshot passed to Assessor must have all required fields populated. Prevents malformed inputs silently reaching evaluators. | During hexagonal arch refactor — assert port contracts at every boundary to catch wiring mistakes early. |
| [Statistical debugging](https://www.debuggingbook.org/html/StatisticalDebugger.html) | Correlate test pass/fail outcomes with which code paths or predicates were exercised to rank suspicious locations. | Run invariant suite across a corpus of known-good and known-bad S3 configs. If a rule fires on 80% of known-good configs, the predicate is miscalibrated. Rank rules by false-positive rate. | After adding a batch of new invariants — validate signal quality before shipping a profile. |
| [Delta debugging](https://www.debuggingbook.org/html/DeltaDebugger.html) | Systematically bisect a failure-inducing input to find the minimal subset that still reproduces the failure. | Given a complex S3 config that triggers (or fails to trigger) a rule, remove fields one by one to find the minimal reproducing fixture. Codify that as the canonical test case for the rule. | A rule behaves unexpectedly on a real-world config. Strip it down to a minimal fixture before filing a bug. |
| [DDSET](https://www.debuggingbook.org/html/DDSetDebugger.html) | Generalize from a specific failure-inducing input to a pattern — replace concrete values with their category to get "fails for all inputs of this form." | After delta debugging yields a minimal config, ask: which fields are load-bearing vs incidental? Generalizes to "any bucket where acl=public-read AND encryption is absent" — confirms the invariant predicate is correctly scoped. | Designing or auditing compound invariants. Use as a design checklist: can you state the minimal triggering pattern? If not, the rule is over-specified. |
| [Slicing](https://www.debuggingbook.org/html/Slicer.html) | Given a variable of interest, compute the backwards slice — only the statements that could have affected its value. | When a risk score is wrong, trace back which invariant results fed the compound scorer, then which config fields fed those invariants. Maps directly to Stave's Assessor → RiskEngine chain. | A final risk score is surprising. Use slicing mentally (or with tracing) to identify which upstream evaluation step produced the wrong intermediate value. |
| [Tracking origins](https://www.debuggingbook.org/html/Intro_Debugging.html) | Tag data values with their provenance and propagate the tag through computations — taint analysis. | Track which source field in the snapshot produced each finding. Every Reporter output should be traceable to a specific snapshot field, not just "invariant X fired." Enables the inspectable reasoning differentiator. | Implementing Reporter output. Every finding should carry field-level provenance — this is what separates Stave from black-box scanners. |
| [Mining specs](https://www.debuggingbook.org/html/SpecFuzzer.html) | Infer function pre/postconditions by observing behavior across many inputs — extract implicit contracts. | Future: run Stave across a large corpus of public S3 configs and mine which attribute combinations are universally absent in clean configs. Candidate new invariants with empirical backing. | Invariant discovery phase. Not v0.x — relevant once you have enough real-world config data to learn from. |
| [Concolic fuzzing](https://www.debuggingbook.org/html/ConcolicFuzzer.html) | Combine concrete execution with symbolic reasoning to systematically generate inputs that cover new branches. | Generate S3 config test fixtures that exercise every branch of every invariant predicate. Ensures full predicate coverage without hand-writing every fixture variant. | Pre-release coverage audit. After invariant authoring stabilizes, verify every predicate branch has a corresponding fixture. |
