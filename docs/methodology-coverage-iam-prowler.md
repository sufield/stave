# Prowler IAM Coverage

Cross-reference of Prowler's 47 AWS IAM checks against Stave's IAM control
catalog, generated by inspecting
`prowler-cloud/prowler/prowler/providers/aws/services/iam/` on the upstream
master branch. The PARTIAL and NOT COVERED rows are the candidate backlog
for future IAM-scope iterations.

Second slice in the broader methodology-coverage effort. S3 is already
published as `methodology-coverage-s3-prowler.md`. EC2 and other services,
plus ScoutSuite's IAM checks, are separate follow-up scans.

## Summary

- **Prowler IAM checks surveyed:** 47
- **COVERED:** 39
- **PARTIAL:** 5
- **NOT COVERED:** 3
- **OUT OF SCOPE:** 0

### Candidate backlog (high-signal gaps, ordered by Prowler severity)

1. **`iam_role_cross_account_readonlyaccess_policy`** (high) — NOT COVERED.
   Prowler specifically flags IAM roles that grant the AWS-managed
   `ReadOnlyAccess` policy to external accounts. Stave's
   `CTL.IAM.TRUST.EXTERNALID.001` and `CTL.IAM.VENDOR.OVERPRIVILEGED.001`
   cover adjacent cross-account patterns but do not specifically detect the
   `ReadOnlyAccess`-to-external-account shape. Needs either a dedicated
   control or extending the existing cross-account controls to flag broad
   read policies.
2. **`iam_root_credentials_management_enabled`** (high) — NOT COVERED. AWS
   Organizations centralized root credentials management (released Nov
   2024) is not captured in the contract or any control. Needs a new
   `organizations.*` namespace or extension to the existing `identity.*`
   account-level fields to record this org-level setting.
3. **`iam_securityaudit_role_created`** (low) — NOT COVERED. Existence
   check for the `SecurityAudit` AWS-managed policy having at least one
   role attached. Symmetric to `CTL.IAM.SUPPORT.001` which shipped for the
   `AWSSupportAccess` role; a parallel control for SecurityAudit would
   close this gap.

The six service-wildcard Prowler checks (`iam_inline_policy_no_full_access_to_cloudtrail`,
`iam_inline_policy_no_full_access_to_kms`,
`iam_inline_policy_no_wildcard_marketplace_subscribe`,
`iam_policy_no_full_access_to_cloudtrail`,
`iam_policy_no_full_access_to_kms`,
`iam_policy_no_wildcard_marketplace_subscribe`) previously flagged as a
single structural gap are now CLOSED by
`CTL.IAM.POLICY.SERVICEWILDCARD.001`, a parameterized control keyed on
`params.denied_service_wildcards: [cloudtrail, kms, aws-marketplace]`.
Operators extend the list as new service-wildcard abuse patterns emerge.

### Candidate backlog (PARTIAL items)

- **`iam_check_saml_providers_sts`** (low) — Stave has `CTL.IAM.FEDERATION.001`
  that pushes for federation use but doesn't inventory SAML provider
  presence specifically. Low-priority.
- **`iam_customer_unattached_policy_no_administrative_privileges`** (medium) —
  Stave's `CTL.IAM.POLICY.ADMIN.001` fires on principals with
  `identity.policies.has_admin_access = true`, which is a
  per-principal-attached field. Unattached policies with admin permissions
  are an inventory hygiene concern Stave doesn't currently surface. Needs
  observation of all customer-managed policies regardless of attachment
  state.
- **`iam_role_access_not_stale_to_bedrock`** / **`iam_user_access_not_stale_to_bedrock`** (medium each) — Stave's
  `CTL.IAM.ROLE.PERMISSIONDRIFT.001` detects accumulated unused permissions
  generically but does not carry Bedrock-specific freshness tracking.
  Bedrock-specific is a narrow Prowler addition; the generic control
  arguably covers the spirit.
- **`iam_user_hardware_mfa_enabled`** (high) — Stave's
  `CTL.IAM.MFA.HWKEY.001` requires hardware MFA for **privileged / admin**
  accounts; Prowler requires it for all users. Posture-policy difference,
  not a technical gap — a future iteration could add a tag-gated or
  profile-gated "all users hardware MFA" variant.

## Structural notes

### The one-to-many escalation split

Prowler has **one aggregated check per policy type** for privilege escalation:
`iam_inline_policy_allows_privilege_escalation` and
`iam_policy_allows_privilege_escalation`. Each of those checks internally
enumerates a fixed list of escalation vectors (CreatePolicyVersion,
AttachUserPolicy, PutUserPolicy, AddUserToGroup, AssumeRole with
UpdateAssumeRolePolicy, PassRole with service variations, etc.) and fires
on any match.

Stave is the inverse shape: **one control per technique**, 24 of them under
`controls/iam/escalation/`, plus two aggregated controls
(`CTL.IAM.ESCALATE.CHAIN.001` for multi-step chains, `CTL.IAM.POLICY.ESCALATION.001`
for the rolled-up self-modify signal). Each Prowler escalation check maps
to the **full set** of Stave ESCALATE.* controls that collectively cover
the same techniques. The coverage-table rows for items 8 and 23 enumerate
all 24+2 controls explicitly rather than abbreviating.

This is the same remediation-granularity tradeoff the S3 scan documented
for ACL-write detection (Prowler's `s3_bucket_public_write_acl` maps to
Stave's `PUBLIC.003` + `ACL.FULLCONTROL.001` + `ACL.ESCALATION.001`). The
split means each Stave finding points at the specific permission to remove
rather than handing the operator an undifferentiated "privilege escalation
path detected" alert.

### The service-wildcard gap (closed)

Six Prowler checks detect service-specific wildcard actions in inline or
managed policies: `cloudtrail:*`, `kms:*`, `aws-marketplace:Subscribe` on
`*`. Previously flagged as a structural gap, now closed by
`CTL.IAM.POLICY.SERVICEWILDCARD.001` — a parameterized control keyed on
`params.denied_service_wildcards: [cloudtrail, kms, aws-marketplace]`.
The control fires when the principal's
`identity.policies.service_wildcards_granted` derived field intersects
the denied list, covering inline and customer-managed alike in one
pass. Extend the list per new methodology findings; each added service
closes additional gaps without a new control.

### Posture-policy differences vs coverage gaps

Several PARTIAL items are **posture-policy differences** rather than
technical gaps: `iam_user_hardware_mfa_enabled` (Stave: privileged-only;
Prowler: all users), `iam_customer_unattached_policy_no_administrative_privileges`
(Stave: per-principal-attached; Prowler: policy-inventory-wide),
`iam_role_access_not_stale_to_bedrock` / `iam_user_access_not_stale_to_bedrock`
(Stave: generic permission drift; Prowler: Bedrock-specific staleness).
These reflect choices about scope, not missing detection capability. A
future iteration could add profile-gated variants without replacing the
existing controls — documented here rather than listed as must-close gaps.

## Out of scope for this slice

- **Prowler checks outside the IAM service.** S3 is in
  `methodology-coverage-s3-prowler.md`. EC2, RDS, CloudTrail, KMS,
  Organizations, and every other service will have its own coverage scan.
  This document tracks IAM only.
- **ScoutSuite's IAM rules.** ScoutSuite may cover IAM configurations
  Prowler does not; a follow-up scan will diff ScoutSuite against both
  Prowler and Stave to surface ScoutSuite-unique checks.
- **Cross-cutting checks that span IAM and other services.** Prowler's
  IAM service directory did not contain any cross-cutting checks at the
  time of this scan; if future checks span services (e.g., an IAM check
  that also evaluates an S3 bucket policy or a KMS key policy), this
  document's scope boundary may need revisiting.
- **CIS Benchmarks, AWS Foundational Security Best Practices, and other
  external frameworks.** Those are separate corpora with their own
  coverage-tracking story.
