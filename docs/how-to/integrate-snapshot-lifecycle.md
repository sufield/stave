# Integrate snapshot lifecycle actions

Stave plans retention. It does not delete or move snapshot files.
External tools consume Stave's JSON output and execute the
recommended actions. This how-to walks through three concrete
integration patterns.

The contracts these examples pin against:

* [`docs/contracts/snapshot-plan.schema.json`](../contracts/snapshot-plan.schema.json)
  — per-file fields produced by `stave snapshot plan --format json`.
* [`docs/contracts/snapshot-inventory.schema.json`](../contracts/snapshot-inventory.schema.json)
  — per-file fields produced by `stave snapshot inventory --format json`.

Both schemas are stable — fields may be added, but never removed or
renamed. See [the contracts README](../contracts/README.md) for the
full versioning policy.

## 1. Bash + jq — delete files past retention

Drop this in a cron job. Stave produces the plan; `jq` filters to the
`delete` recommendations; `xargs rm` runs the deletions.

```bash
#!/usr/bin/env bash
set -euo pipefail

OBS_ROOT="/data/obs"

stave snapshot plan --observations-root "$OBS_ROOT" --format json \
  | jq -r '.files[] | select(.action == "delete") | .file_path' \
  | xargs --no-run-if-empty rm -v
```

Notes:

* `.files[]` traverses the per-entry array. Drop the `.files` if you
  prefer raw newline-delimited entries — but the plan output is one
  envelope object, so `.files[]` is the canonical access.
* `--no-run-if-empty` keeps `xargs` quiet on a clean run with zero
  deletions. Without it, GNU `xargs` invokes `rm` once with no
  arguments and prints a usage error.
* Pipe `stderr` of the cron job to your alerting system; Stave logs
  schema-validation issues that you'll want to see before they
  produce surprises.

## 2. Bash + jq — archive files past retention

Same plan, different fate: move past-retention files into a sibling
archive root. The plan command emits `delete` for everything past the
threshold (Stave's plan does not differentiate delete vs archive —
the **inventory** command does that, using quality signals). For a
"move everything past retention into archive" workflow, the plan is
sufficient.

```bash
#!/usr/bin/env bash
set -euo pipefail

OBS_ROOT="/data/obs"
ARCHIVE_ROOT="/data/archive"

mkdir -p "$ARCHIVE_ROOT"

stave snapshot plan --observations-root "$OBS_ROOT" --format json \
  | jq -r '.files[] | select(.action == "delete") | .file_path' \
  | while IFS= read -r src; do
      mv -v "$src" "$ARCHIVE_ROOT/$(basename "$src")"
    done
```

Use the **inventory** command if you want the richer `keep` / `archive`
/ `delete` / `review` split that takes per-snapshot quality into
account:

```bash
stave snapshot inventory --observations-dir /data/obs --format json \
  | jq -r '.snapshots[] | select(.action == "archive") | .file_path' \
  | while IFS= read -r src; do
      mv -v "$src" "/data/archive/$(basename "$src")"
    done
```

The inventory output additionally surfaces `quality_warnings` and
`assessment_status` per file — a `review` action with
`assessment_status == "pending"` is a strong signal to delay
archival until the snapshot has been evaluated.

## 3. GitHub Actions — scheduled cleanup with PR

Run Stave on a schedule, execute the deletions in a feature branch,
and open a PR so a human can review the diff before merging. This is
the pattern most teams want for production observation directories.

```yaml
name: Snapshot retention cleanup

on:
  schedule:
    - cron: '0 6 * * 1'   # weekly, Monday 06:00 UTC
  workflow_dispatch:

permissions:
  contents: write
  pull-requests: write

jobs:
  retention:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install stave
        run: |
          curl -sSL https://stave.dev/install.sh | bash
          echo "$HOME/.stave/bin" >> "$GITHUB_PATH"

      - name: Plan retention
        id: plan
        run: |
          stave snapshot plan \
            --observations-root observations \
            --format json > /tmp/plan.json
          deletions=$(jq '[.files[] | select(.action == "delete")] | length' /tmp/plan.json)
          echo "deletions=$deletions" >> "$GITHUB_OUTPUT"

      - name: Apply deletions
        if: steps.plan.outputs.deletions != '0'
        run: |
          jq -r '.files[] | select(.action == "delete") | .file_path' /tmp/plan.json \
            | xargs --no-run-if-empty rm -v

      - name: Open PR with deletions
        if: steps.plan.outputs.deletions != '0'
        uses: peter-evans/create-pull-request@v6
        with:
          branch: snapshot-retention
          title: "chore(observations): retention cleanup (${{ steps.plan.outputs.deletions }} files)"
          body: |
            Generated by `stave snapshot plan --format json` on ${{ github.event.schedule }}.
            Plan output is attached as `plan.json` for audit.
          add-paths: observations/
          commit-message: |
            chore(observations): apply retention plan
```

Notes:

* The `$id` field on the schema doubles as a permanent reference
  for the contract — bake it into your tool's pin (e.g. through
  `jsonschema`'s `$ref` resolver).
* The plan / inventory JSON is order-stable per command run but not
  guaranteed across runs. Sort by `file_path` before diffing if
  you're producing a deterministic audit log.
* The exit code is `0` regardless of how many files are flagged for
  action — Stave reserves non-zero codes for invalid input or
  internal errors. Use `jq` to check the action count, as the
  example above does.
